# 8주차 스터디 회고

이번 주에는 로그인한 회원의 즐겨찾기를 구현하고, 평점과 즐겨찾기를 한 번에 저장하는 과정에서 트랜잭션이 필요한 이유를 확인했습니다.

## 이번 주에 구현한 흐름

회원이 로그인하면 서버는 JWT를 발급합니다. 이후 즐겨찾기 요청에서는 회원 ID를 본문으로 보내지 않고 Bearer 토큰을 전달합니다. 글로벌 Guard가 서명과 만료를 검증한 뒤, 컨트롤러는 `@LoginMember()`로 인증된 회원 ID를 받습니다.

즐겨찾기 Service는 이 회원 ID를 조회·삭제 조건에 포함합니다. 따라서 A가 보관한 영화가 B의 목록에 나오지 않고, B가 같은 영화 ID로 삭제해도 A의 데이터는 지워지지 않습니다. 영화 ID가 같더라도 회원이 다르면 별개의 즐겨찾기이므로 두 회원 모두 등록할 수 있습니다.

## 트랜잭션을 적용한 이유

영화 기록은 사용자가 “평점을 남기면서 즐겨찾기에도 보관한다”는 한 번의 행동입니다. 평점을 저장한 뒤 즐겨찾기 저장에서 실패했는데 평점만 남으면 사용자가 요청한 동작의 일부만 완료됩니다.

두 Service를 순서대로 호출하는 것만으로는 두 저장이 같은 트랜잭션에 속한다고 보장할 수 없습니다. 그래서 영화 기록 전용 Service를 만들고 `dataSource.transaction()` 안에서 두 INSERT를 실행했습니다. 콜백에서 받은 manager의 Repository만 사용하여 같은 DB 연결에 참여하도록 했습니다. 정상 종료하면 commit하고, 예외가 발생하면 앞선 변경까지 rollback합니다.

실제로 확인하기 위해 즐겨찾기 INSERT에 임시 오류를 발생시켰습니다. 요청 직전 평점·즐겨찾기가 각각 0건이었고, 실패 응답 이후에도 모두 0건이었습니다. 트리거를 제거한 뒤에는 같은 요청이 정상적으로 성공했습니다. 이 검증을 통해 단순히 중복 요청을 거절하는 것과, 저장 도중 발생한 실패를 롤백하는 것은 다른 검사라는 점을 확인했습니다.

## 사전 검사와 UNIQUE의 차이

사전 조회는 사용자에게 의미 있는 오류를 알려주는 데 도움이 됩니다. 다만 두 요청이 거의 동시에 도착하면 둘 다 “아직 없다”는 결과를 보고 INSERT를 시도할 수 있습니다.

최종 중복 방지는 DB의 `UNIQUE(member_id, movie_id)`가 담당합니다. 서비스에서 한 번 검사하고, DB 제약 오류도 같은 `FAVORITE409_1`로 변환했습니다. 등록 요청 8개를 동시에 실행했을 때 한 요청만 성공하고 DB에는 한 행만 남았습니다.

트랜잭션이 있다고 해서 동일한 값의 중복 INSERT가 자동으로 금지되는 것은 아닙니다. 트랜잭션은 관련 작업의 성공·실패를 묶고, UNIQUE는 저장할 데이터가 지켜야 할 규칙을 강제합니다.

## 응답 규칙에서 배운 점

토큰이 없으면 요청자를 확인할 수 없으므로 401입니다. 본인에게 해제할 즐겨찾기가 없으면 404입니다. 같은 영화를 다시 등록하면 409입니다. 반면 아직 보관하지 않은 영화의 여부를 물어보는 요청은 정상적인 질문이므로 200과 `isFavorite: false`를 반환합니다.

빈 목록도 200과 `[]`로 반환했습니다. 정상적으로 데이터가 없는 상황과 실제 실패를 구분하면 화면에서 예외 처리와 빈 상태 안내를 다르게 구현할 수 있습니다.

## 선택 미션에서 배운 점

Swagger에 URL만 나열하면 요청을 재현하기 어렵습니다. 요청 본문, Bearer 인증 여부, 성공 응답과 HTTP 상태별 업무 코드를 함께 적었습니다. 실제 UI에서 토큰을 설정하고 호출하여 문서의 예시와 서버 응답이 맞는지도 확인했습니다.

검증 과정에서는 기존 인증·평점 기능을 포함한 통합 테스트 24개와 Postman의 19개 요청·47개 검사가 모두 통과했습니다. 이번 주에는 API가 성공하는지만 보는 데서 더 나아가, 다른 회원에게 데이터가 노출되지 않는지와 실패 후 DB 상태까지 확인했습니다.

## 스터디에서 이야기할 질문

- 이미 즐겨찾기한 영화를 영화 기록으로 저장할 때, 409로 거절하는 정책과 기존 즐겨찾기를 재사용하는 정책은 사용자 경험에 어떤 차이를 만들까요? 이번에는 워크북에 따라 409로 구현했습니다.
- 평점과 즐겨찾기 중 하나만 실패해도 전체를 취소해야 하는 범위는 어디까지일까요? 추후 알림처럼 외부 서비스가 추가되면 같은 DB 트랜잭션만으로 처리할 수 있을까요?
- 평점 수정에서 마지막 요청이 앞선 수정을 덮어쓰는 문제가 생긴다면, 버전 비교를 이용한 낙관적 잠금을 어떻게 적용할 수 있을까요?

## 발표할 때 사용할 설명

“이번 주에는 JWT로 확인한 회원의 즐겨찾기 API 네 개와 영화 기록 저장 API를 만들었습니다. 평점과 즐겨찾기는 한 번의 사용자 행동이어서 하나의 트랜잭션으로 묶었습니다. 두 번째 저장을 실제로 실패시킨 뒤 DB를 확인했을 때 첫 저장도 남지 않아 롤백을 검증할 수 있었습니다. 동시에 같은 즐겨찾기를 등록하는 경우에는 트랜잭션과 별개로 복합 UNIQUE가 필요하다는 점도 확인했습니다. 선택 미션으로 Swagger에서 인증 방식과 요청·성공·실패 응답을 문서화했습니다.”
