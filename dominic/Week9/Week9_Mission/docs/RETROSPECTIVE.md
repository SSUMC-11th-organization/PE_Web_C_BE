# 9주차 스터디 회고

## 1분 발표용입니다

이번 주차에는 8주차에 만든 영화 API의 Swagger 문서를 보완하고, 단위 테스트와 통합 테스트를 작성했습니다. 단위 테스트에서는 가짜 Repository로 중복 평점과 다른 회원의 수정 요청이 차단되는지 확인했고, 통합 테스트에서는 메모리 DB와 실제 JWT를 사용해 HTTP 요청부터 저장까지 검증했습니다.

가장 기억에 남는 부분은 트랜잭션 테스트였습니다. 처음에는 실패 후 평점이 없으면 충분하다고 생각했지만, 저장 전에 중복을 검사하면 트랜잭션이 없어도 같은 결과가 나온다는 점을 알게 됐습니다. 그래서 평점 저장 뒤에 즐겨찾기 충돌이 발생하도록 만들고, 트랜잭션을 제거했을 때 평점이 1건 남아 테스트가 실패하는 결과를 확인했습니다.

최종적으로 단위 4개와 통합 14개를 통과했고, 기존 MySQL 테스트도 확인했습니다. 이번에는 테스트가 통과하는 것뿐 아니라, 실제 실수를 넣었을 때 실패하는지와 실패 후 데이터가 어떻게 남는지까지 확인해야 한다는 점을 배웠습니다.

## 더 자세히 이야기할 내용입니다

**이번에 한 일**: 평점 CRUD·회원 정보·즐겨찾기 API 설명, 토큰 표시와 상태별 code 예제를 보완했습니다. 전체 15개 API의 문서 계약도 통합 테스트에서 확인했습니다.

**단위와 통합 테스트의 차이**: 단위 테스트는 가짜 Repository로 서비스의 판단과 저장 미호출을 빠르게 확인했습니다. 통합 테스트는 실제 회원가입·로그인·Guard·ValidationPipe·서비스·DB를 연결해 서비스 테스트로는 알 수 없는 URL, HTTP 상태, 인증, 입력 검증을 확인했습니다.

**가장 크게 배운 점**: 409 응답만 확인하는 테스트는 트랜잭션 제거를 잡지 못했습니다. 같은 409라도 평점이 남는 경우를 구분하려면 요청 후 DB 상태를 직접 검사해야 했습니다. 또한 실패 지점이 첫 INSERT 뒤에 있어야 실제 롤백이 검증됐습니다.

**테스트 대역에서 신경 쓴 점**: 중복 상황만 설정하고 save의 반환값을 비워 두면 검사를 제거했을 때 TypeError 때문에 실패할 수 있습니다. save가 정상 값을 반환하도록 준비해, 잘못 저장을 허용했다는 동작 자체를 검증하도록 했습니다.

**메모리 DB의 한계**: sql.js와 MySQL은 기본 키와 예외 형태가 달랐습니다. 제거 실험에서 SQLite UNIQUE 오류가 500으로 반환된 사실을 MySQL 동작과 구분했습니다. MySQL의 동시성, 실제 두 번째 INSERT 실패와 롤백은 별도 회귀 테스트로 확인했습니다.

**스터디에서 나눌 질문**: DB UNIQUE와 오류 변환이 이미 중복 요청을 409로 막는다면 서비스 사전 중복 검사가 지워져도 HTTP 통합 테스트는 통과할 수 있습니다. 이때 단위 테스트로 서비스 규칙을 확인하는 이유와, 외부 계약만 유지되면 허용할 구현 변경의 범위를 어떻게 정할지 이야기해 보고 싶습니다.

**다음에 보완할 점**: 배포 설정을 바꾸기 전에도 같은 테스트를 실행하고, 프론트와 연결할 때는 브라우저 CORS 동작을 직접 확인하려고 합니다. 메모리 테스트의 편의성과 실제 DB 검증의 역할을 구분해서 유지하려고 합니다.
