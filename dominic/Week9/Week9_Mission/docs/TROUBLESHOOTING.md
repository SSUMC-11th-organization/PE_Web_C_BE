# 9주차 트러블슈팅

## No.1 · 사전 검사만으로는 트랜잭션 롤백을 증명할 수 없었습니다

**이슈**: 기존 즐겨찾기 충돌 테스트가 트랜잭션 제거를 잡지 못할 수 있는 구조였습니다.

**문제**: 8주차 서비스는 즐겨찾기 중복을 평점 INSERT보다 먼저 확인했습니다. 이미 즐겨찾기한 영화를 요청하면 저장 전에 예외가 발생하므로, 평점이 0건이라는 결과만으로는 롤백이 동작했는지 판단할 수 없었습니다.

**해결**: 하나의 트랜잭션 안에서 평점을 먼저 INSERT하고, 그다음 즐겨찾기 중복 검사와 저장을 수행하도록 순서를 조정했습니다. 테스트에서는 HTTP 409 / FAVORITE409_1뿐 아니라 평점 전체 개수, 해당 회원·영화의 평점 개수, 기존 즐겨찾기 개수까지 확인했습니다.

임시 복사본에서 트랜잭션을 제거하자 HTTP 응답은 409였지만 평점이 1건 남아 `Expected: 0 / Received: 1`로 실패했습니다. 원복 후 통합 테스트 14개가 모두 통과했습니다.

**참고**: [영화 기록 서비스](../src/movie-records/movie-records.service.ts), [실패 로그](mutation-transaction-e2e.txt), [실패 캡처](screenshots/09-transaction-removed-failed.jpg)

## No.2 · 메모리 DB와 MySQL의 ID 표현을 맞춰야 했습니다

**이슈**: 같은 엔티티를 사용하면서도 DB별 자동 증가 기본 키와 반환 타입 차이를 처리해야 했습니다.

**문제**: 프로덕션은 MySQL BIGINT와 문자열 ID를 사용합니다. sql.js는 자동 증가 기본 키에 INTEGER가 필요하고 숫자로 값을 반환할 수 있어, 회원 ID를 문자열로 비교하는 서비스와 차이가 생길 수 있었습니다.

**해결**: 테스트 전용 MemoryDataSource에서 자동 증가 BIGINT 기본 키만 INTEGER로 바꾸고, BIGINT 컬럼 조회값은 문자열로 정규화했습니다. 엔티티의 관계와 복합 UNIQUE는 그대로 사용했으며 실제 MySQL 설정은 변경하지 않았습니다. 매 테스트 전에 스키마를 새로 만들고 종료 시 연결을 닫았습니다.

이 방식의 한계도 문서에 적었습니다. SQLite는 MySQL의 격리 수준이나 동시성 검증을 대체할 수 없어 기존 MySQL 회귀 테스트 24개를 별도로 실행했습니다.

**참고**: [테스트 앱](../test/support/test-app.ts), [TypeORM sql.js 문서](https://typeorm.io/docs/drivers/sqlite/)

## No.3 · 중복 검사 제거 실험에서 실패 원인을 구분했습니다

**이슈**: 즐겨찾기 중복 검사를 제거한 통합 테스트가 409 대신 500을 반환했습니다.

**문제**: sql.js에서도 복합 UNIQUE가 남아 있어 중복 INSERT는 차단됐습니다. 다만 기존 예외 필터는 MySQL의 ER_DUP_ENTRY를 변환하므로 SQLite UNIQUE 예외는 COMMON500으로 처리됐습니다. 이를 중복 데이터가 저장된 것으로 해석하면 실제 결과와 다른 설명이 됩니다.

**해결**: 정상 코드의 서비스 중복 검사를 유지하고 제거 실험은 임시 복사본에서만 수행했습니다. 단위 테스트는 예외 대신 정상 응답을 받은 점으로, 메모리 DB 통합 테스트는 409 응답 계약이 깨진 점으로 실패했다는 사실을 구분해 기록했습니다. 실제 MySQL의 UNIQUE와 중복 오류 매핑도 별도 회귀 테스트로 확인했습니다.

가짜 Repository의 save에는 정상 반환값을 기본으로 설정하여, 검사를 제거했을 때 불완전한 Mock 때문에 TypeError가 발생하는 대신 잘못 허용된 저장 응답을 명확하게 확인하도록 보완했습니다. 원복 후 단위 4개·통합 14개를 모두 통과했습니다.

**참고**: [단위 실패 로그](mutation-favorite-unit.txt), [통합 실패 로그](mutation-favorite-e2e.txt), [MySQL 회귀 결과](mysql-test-results.txt)
