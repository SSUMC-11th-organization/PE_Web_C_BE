# 9주차 미션 기록 · 함께 테스트하고 다듬기

[워크북](https://makeus-challenge.notion.site/9-2deb57f4596b83bcb2f681f4382bfd21) · [이슈 #37](https://github.com/SSUMC-11th-organization/PE_Web_C_BE/issues/37)

## 1. 이번 주차에서 확인한 목표입니다

8주차에 구현한 회원·JWT 인증·평점·즐겨찾기·영화 기록 API를 이어서 사용했습니다. 이번에는 기능을 추가하는 것에서 더 나아가, 다른 사람이 Swagger만 보고 API를 사용할 수 있도록 설명을 보완하고 기존 동작을 테스트 코드로 고정하는 데 집중했습니다.

워크북을 읽고 실습, 필수 미션, 선택 미션을 나누어 확인했습니다. 필수 미션은 남아 있던 API 문서화와 평점 서비스 단위 테스트 2개, 평점 등록 통합 테스트 2개였습니다. 선택 미션은 영화 기록 저장 실패 시 앞서 저장한 평점도 롤백되는지 확인하고, 트랜잭션을 제거했을 때 테스트가 실패하는 증빙을 남기는 것이었습니다.

이전 8주차 PR과 섞이지 않도록 `dominic/main`을 기준으로 9주차 작업 공간을 만들고, `dominic/Week9/Week9_Mission`에 독립적으로 실행 가능한 프로젝트를 준비했습니다. 이슈는 `Chapter09_함께 테스트하고 다듬기`, 브랜치는 `dominic/#37`로 컨벤션을 맞췄습니다.

## 2. Swagger 문서를 보완했습니다

문서 주소를 워크북에 맞게 `/swagger-ui`로 제공하고 기존 `/docs`도 유지했습니다. 공통 ValidationPipe와 예외 필터 설정, OpenAPI 문서 생성 함수를 분리하여 서버와 통합 테스트가 같은 설정을 사용하도록 구성했습니다.

평점 등록·수정·삭제와 회원별 평점 조회, 내 정보 조회·수정, 즐겨찾기 목록·여부·해제에 설명을 작성했습니다. 전체 15개 API에 공개 여부와 성공·실패 HTTP 상태, 응답의 `code` 예제를 넣었습니다. 평점과 닉네임 수정 DTO에도 예시와 입력 제약을 추가했습니다.

회원가입·로그인·닉네임/이메일 중복 확인·회원별 평점 조회는 공개 API로 표시했습니다. 나머지 API에는 Bearer 인증을 표시하고, 회원 ID를 요청 본문으로 받지 않고 JWT의 sub로 결정한다는 점을 설명했습니다. 회원별 평점 조회가 쿼리 유무에 따라 배열 또는 페이지 객체를 반환한다는 점도 적었습니다.

실제 Swagger 화면에서 테스트 회원을 가입시키고 로그인했습니다. 발급받은 accessToken을 Authorize에 입력하여 즐겨찾기 등록의 201 / COMMON201 응답과 동일 영화 재등록의 409 / FAVORITE409_1 응답을 확인했습니다. JWT가 노출되는 Curl 영역을 제외하고 서버 응답 영역을 캡처했습니다.

## 3. 가짜 Repository로 단위 테스트를 작성했습니다

NestJS TestingModule에 `getRepositoryToken`과 `useValue`를 사용해 실제 DB 대신 가짜 Repository를 주입했습니다. `jest.fn()`으로 조회 결과를 준비하고 저장 호출을 확인했습니다. 테스트 본문은 given, when, then 흐름으로 나눴습니다.

즐겨찾기는 처음 등록할 때 한 번 저장하는 경우와, 이미 등록한 영화라면 409 / FAVORITE409_1을 발생시키고 저장하지 않는 경우를 검증했습니다.

필수 평점 테스트에서는 같은 영화에 중복 등록할 때 409 / RATING409_1이 발생하는지 확인했습니다. 다른 회원의 평점을 수정하려 할 때는 403 / RATING403_1이 발생하고, 기존 점수가 바뀌지 않으며 save도 호출되지 않는지 확인했습니다. 단위 테스트는 총 4개를 통과했습니다.

## 4. 테스트 전용 메모리 DB로 통합 테스트를 작성했습니다

개발용 MySQL에 테스트 데이터를 섞지 않도록 sql.js 메모리 DB를 사용했습니다. 실제 회원가입과 로그인을 거쳐 JWT를 발급하고, Supertest로 HTTP 요청을 보냈습니다. Guard와 서비스는 대체하지 않았으며, 실제 인증·입력 검증·예외 처리·Repository 저장까지 연결했습니다.

MySQL의 BIGINT 자동 증가 기본 키와 sql.js의 INTEGER 자동 증가 방식이 달라 테스트 전용 DataSource에서 해당 컬럼만 변환했습니다. BIGINT 조회값도 문자열로 맞춰 MySQL에서 사용하던 회원 ID 비교가 동일하게 작동하도록 했습니다. 프로덕션 엔티티와 MySQL 스키마는 유지했습니다.

각 테스트 전에 메모리 스키마를 새로 만들어 실행 순서에 영향을 받지 않도록 했습니다. 토큰 없는 즐겨찾기 등록, 정상 등록, 중복 등록, 등록하지 않은 영화의 isFavorite false를 먼저 검증했습니다.

필수 평점 통합 테스트에서는 토큰 없는 `POST /ratings`의 401 / AUTH401_2와 토큰을 포함한 요청의 201 / COMMON201을 확인했습니다. 응답뿐 아니라 저장된 평점의 회원과 점수도 확인했습니다. 중복 평점, 다른 회원 수정 거절, 수정·조회·삭제, 잘못된 입력과 위조 토큰까지 확장하여 통합 테스트 14개를 통과했습니다.

## 5. 선택 미션에서 롤백을 증명했습니다

기존 코드는 즐겨찾기 중복을 평점 INSERT 전에 검사하고 있었습니다. 이 순서에서는 실패 전에 저장한 데이터가 없어, 트랜잭션을 제거해도 평점 0건이라는 테스트가 통과할 수 있었습니다. 따라서 롤백을 실제로 검증하려면 첫 저장 이후에 실패하도록 구성해야 한다고 판단했습니다.

영화 기록 서비스에서 평점을 먼저 저장하고, 같은 트랜잭션 안에서 즐겨찾기의 중복을 검사·저장하도록 순서를 정리했습니다. 이미 즐겨찾기한 영화에 `addToFavorites: true`로 요청하면 FAVORITE409_1이 발생하고, 앞서 INSERT한 평점도 롤백됩니다.

통합 테스트에서는 기존 즐겨찾기 1건과 평점 0건을 준비했습니다. 요청 후 409 상태와 FAVORITE409_1을 확인하고, 평점 전체 개수와 해당 회원·영화의 평점 개수가 그대로인지 확인했습니다. 기존 즐겨찾기 1건도 보존되는지 확인했습니다.

임시 복사본에서 트랜잭션을 제거하고 같은 테스트를 실행했습니다. HTTP 409 응답은 유지됐지만, 평점이 1건 남아 `Expected: 0 / Received: 1`로 실패했습니다. 이 결과를 통해 오류 응답만 확인하면 일부 데이터가 남는 문제를 놓칠 수 있다는 점을 확인했습니다. 원복 후 전체 테스트가 다시 통과하는 결과도 남겼습니다.

## 6. 일부러 중복 검사를 제거해 봤습니다

원본 소스를 직접 변경하지 않도록 임시 디렉터리에 프로젝트를 복사한 뒤 즐겨찾기 중복 검사만 제거했습니다. 단위 테스트는 FAVORITE409_1 예외를 기대했지만 정상 저장 응답을 받아 실패했습니다. 통합 테스트도 기대한 409 대신 500을 받아 실패했습니다.

통합 테스트의 실패 원인도 구분해 기록했습니다. sql.js의 UNIQUE 제약이 중복 INSERT를 막았지만, 기존 예외 필터가 MySQL의 ER_DUP_ENTRY를 처리하므로 SQLite 오류는 COMMON500으로 반환됐습니다. 이 결과를 중복 데이터가 저장되었다는 뜻으로 해석하지 않았습니다. 실제 MySQL에서는 DB UNIQUE와 중복 오류 매핑이 추가 방어 역할을 하고 있었습니다.

중복 검사와 트랜잭션 실험을 마친 뒤 복사본을 원복하고 단위 4개·통합 14개를 다시 통과시켰습니다. 실험 스크립트는 기대한 실패 메시지까지 확인하며, 작업 소스와 MySQL에는 변경을 가하지 않습니다.

## 7. 최종 검증과 제출 자료를 정리했습니다

빌드와 테스트 코드 타입 검사를 통과했습니다. 단위 테스트 4개, 메모리 DB 통합 테스트 14개, 기존 MySQL 회귀 테스트 24개를 통과했습니다. Postman/Newman 시나리오도 19개 요청과 47개 검증을 모두 통과했습니다.

MySQL에서는 임시 트리거로 즐겨찾기 INSERT를 강제로 실패시켜 평점과 즐겨찾기가 모두 0건으로 남는지 확인했습니다. 동일 즐겨찾기 동시 요청에서도 한 건만 저장되는 기존 검증을 유지했습니다. 이 검증을 통해 메모리 DB 테스트가 MySQL의 모든 특성을 대신하지는 않는다는 점도 확인했습니다.

Swagger 문서, 실제 201·409 응답, 전체 테스트 통과, 중복 검사 제거 실패, 트랜잭션 제거 실패, 원복 후 통과 화면을 `docs/screenshots`에 저장했습니다. 테스트 캡처는 실제 실행 로그를 보여주는 로컬 증빙 페이지에서 촬영했으며, 원본 로그도 함께 보관했습니다.

핵심 키워드는 항목별 3줄 이내로 정리했습니다. 트러블슈팅과 스터디에서 읽을 수 있는 1분 회고도 별도 파일에 작성했습니다. 이번 주차에는 성공 응답을 확인하는 것에서 더 나아가, 실패 후 상태가 유지되는지와 테스트가 실제 실수를 잡는지까지 검증하는 방법을 배웠습니다.
