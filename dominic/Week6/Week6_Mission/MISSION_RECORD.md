# 6주차 미션 기록 — 입력한 데이터를 저장하기

## 목표와 준비

5주차 영화 평점 API를 별도 6주차 프로젝트로 이어받아 회원가입과 평점 등록·수정·삭제 API를 구현했습니다. 기존 5주차 PR은 아직 열려 있어 기존 코드를 복사했으며, 데이터는 별도 `umc_movie_week6` MySQL 실습 DB에서 검증했습니다.

## 회원가입 구현

`POST /members`에 이메일, 닉네임, 비밀번호를 전달하도록 했습니다. DTO에서 이메일 형식과 길이, 닉네임 2~12자, 비밀번호 8자 이상 및 영문 대·소문자·숫자·특수문자 포함 여부를 검사했습니다. bcrypt의 입력 제한을 고려해 72바이트가 넘는 비밀번호도 거부했습니다.

Service에서 이메일·닉네임 중복을 각각 확인한 뒤 비밀번호를 bcrypt cost 10으로 해시해 저장했습니다. 성공 응답에는 회원 ID, 이메일, 닉네임만 포함하고 비밀번호를 제외했습니다. 실제 DB에서 60자 해시가 저장됐고 입력한 테스트 비밀번호와 bcrypt 비교가 성공하는 것을 확인했습니다.

## 평점 CRUD

`POST /members/{memberId}/ratings`로 평점을 등록하고, `PATCH /members/{memberId}/ratings/{ratingId}`로 수정하며, `DELETE`로 삭제하도록 구현했습니다. 영화 ID는 양의 정수, 점수는 1~5의 정수, 후기는 선택 사항이며 500자 이하로 제한했습니다. 수정 시 후기를 생략하면 기존 값을 유지하고 `null`을 보내면 삭제합니다.

이미 같은 회원이 같은 영화에 평점을 남겼으면 409, 다른 회원 ID로 수정·삭제하면 403, 존재하지 않는 평점이면 404를 반환합니다. 삭제 성공은 응답 본문 없는 204로 확인했습니다. 현재 memberId는 클라이언트가 직접 지정하므로 실제 사용자 인증은 보장하지 못하며, 다음 주차 인증이 필요합니다.

## 공통 응답과 선택 미션

성공과 실패는 `isSuccess`, `code`, `message`, `result` 필드로 통일했습니다. 단 204는 본문을 보내지 않습니다. 이메일 중복은 `MEMBER4091`, 닉네임 중복은 `MEMBER4092`, 평점 중복은 `RATING4091`로 구분했습니다.

사전 중복 확인 후 동시에 요청이 들어오는 상황을 고려해, DB의 `ER_DUP_ENTRY` 오류도 전역 Exception Filter에서 해당 409 응답으로 변환했습니다. 같은 이메일로 8건을 동시에 보냈을 때 1건만 생성되고 7건이 `MEMBER4091`로 반환됐습니다. 이때 서버 로그에서 DB UNIQUE 위반이 필터에 의해 변환된 것을 확인했고, DB에서 해당 이메일이 한 건만 저장된 것도 검사했습니다.

## 실제 확인 결과

- 브라우저 간이 화면에서 회원가입과 평점 등록 각각 201, 형식 오류 400, 동시 가입 1건 성공·7건 중복을 확인했습니다. [성공·동시 요청 캡처](docs/browser-success-race.jpg), [검증 실패 캡처](docs/browser-validation.jpg)
- HTTP·MySQL 통합 테스트에서 해시 비교, 중복 이메일·닉네임, 잘못된 점수·후기, 회원 없음, 소유자 불일치, 평점 없음, 수정 후 조회, 본문 없는 204와 삭제 후 조회를 확인했습니다.
- 실제 MySQL 중복 이메일·닉네임·평점 오류를 발생시켜 전역 필터의 오류 변환을 검사했고, 회원가입 동시 요청과 CORS preflight도 확인했습니다.
- `npm run build` 및 `npm test`가 통과했습니다. 테스트와 간이 화면은 6주차 실습 DB에 테스트 회원을 생성합니다.

## 트러블슈팅

로컬 MySQL 접근 시 실행 환경의 네트워크 제한으로 연결이 거부됐습니다. 필요한 로컬 DB 접근 권한을 받아 6주차 전용 DB를 초기화하고 서버와 테스트를 다시 실행해 해결했습니다.

## 회고

입력 형식 검증, 서비스의 중복 확인, DB UNIQUE 제약은 각각 다른 시점에서 데이터를 지킨다는 점을 이해했습니다. 특히 동시에 들어온 요청은 모두 사전 검사를 통과할 수 있으므로 DB 오류까지 같은 응답 형식으로 처리해야 한다는 점을 확인했습니다. 또한 경로의 memberId와 소유자 비교만으로는 요청자의 신원을 인증할 수 없다는 한계를 확인해, 이후 로그인 토큰 적용이 왜 필요한지 이해했습니다.
